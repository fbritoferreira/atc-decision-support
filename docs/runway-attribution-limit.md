# Why runway attribution cannot be fixed without new data

Status: diagnosed 2026-08-20; the data-model change landed 2026-08-21, and the
US coordinates moved to FAA NASR on 2026-08-24. Real threshold coordinates for
all 62 strips (`runway-ends-data.ts`, generated by
`scripts/gen-runway-geometry.py`; US airports from the FAA NASR 28-day cycle,
the rest from OurAirports; checking the two against each other found KORD
09R/27L's end 3,589 ft short in OurAirports, the 2021 extension missing), an
extended-centreline geometry module, and attribution by nearest centreline
within 0.6 NM cross-track on the live path. A round-trip test pins all 124
ends: an aircraft on any end's own centreline at 2, 5 and 8 NM gets that end
back, DFW's five same-heading strips included. Scenarios keep the legacy
heading-only path, so no scenario output moved. Live re-measurement is the
next window's work; everything below stands as the record of why the change
was needed.

## What the paper currently says

That live ingest resolves only 10 to 15 per cent of ADS-B contacts within 40 NM
into arrivals and departures, that roughly 7 to 25 per cent of approach-phase
arrivals get a runway assigned, and that runway centreline geometry is future
work. All true, and none of it explains why.

## What inferRunway actually does

```
inferRunway(headingDeg, altitudeFt, runways)
  altitudeFt > 5000        -> undefined
  else pick the runway end whose heading is within 20 degrees, nearest first
```

Position is never consulted. The function receives a heading, an altitude and the
runway list, and nothing about where the aircraft is. So attribution is a filter
on two scalars:

- **the 5,000 ft cut** removes aircraft above 5,000 ft, which beyond roughly 15
  NM is most arrivals still on descent. This is the larger half of the coverage
  loss.
- **the 20 degree tolerance** removes aircraft on downwind and base legs, whose
  heading is 90 or 180 degrees off the runway. That exclusion is correct for wake
  pairing, since such an aircraft is not on anyone's final, but it means those
  aircraft are absent from every runway-keyed doctrine, not just wake.

## The part that cannot be tuned away

Parallel runways share a heading, so `headingDelta` is identical for all of them
and the tie is broken by registry order. Every westbound arrival at Atlanta is
assigned to whichever of the four 092-degree strips happens to be listed first.

Measured across the registry:

| | |
|---|---|
| strips sharing a heading with another strip | **51 of 62, 82 per cent** |
| airports with at least one ambiguous group | 12 of 17 |
| US airports with at least one ambiguous group | **10 of 10** |

Worst cases: KDFW has five strips at 184 degrees, KORD has three at 92 and three
at 99, KLAX has four at 69, KATL has four at 92.

Every airport in the measurement set is affected. This is not an edge case; it is
the normal configuration of a large US airport.

## Why the registry cannot resolve it

A runway record carries `id`, `headingDeg`, `lengthFt`, `mode` and
`surfaceFriction`. There is no position: no threshold coordinates, no lateral
offset, nothing that distinguishes 27L from 27R in space. Geometry is expressed
only relative to a single airport reference point.

So no amount of work inside `inferRunway` can separate parallel strips. The
information required is not present. Adding centreline geometry is a data model
change first and an algorithm change second, and the algorithm is the easy half:
cross-track distance from each candidate centreline, nearest wins.

OurAirports, already the source for the runway data in use, publishes runway
endpoint coordinates, so the input exists.

## What this explains downstream

Several findings that looked separate are the same limitation seen from different
angles.

The lateral-stream clustering in the wake doctrine exists because runway labels
could not be trusted to separate parallel approaches. It is a proxy for geometry
the registry does not carry.

The proximity per-pair dump added a `same_runway` column to test whether
proximity volume is parallel approaches. It cannot answer that, because both
aircraft in a parallel pair are labelled with the same runway. The column
inherits the ambiguity.

The runway-end resolution bug had the blast radius it did partly because runway
identity was already carrying more weight than the data could support.

## Sequencing

This is the item with the best ratio of measurement value to risk, because it
widens the population every live claim is computed over. It is also the only open
item that changes an input rather than a threshold, so it wants its own sampling
window rather than being bundled with the wake and proximity fixes.

Order: add runway endpoint coordinates to the registry, then cross-track
attribution in `inferRunway`, then a window measuring coverage before and after.
Coverage is the headline number to report, not alert counts.

## What generating the coordinate file surfaced

Two validation findings from the generation run, kept because they are about
data this project already trusted:

- **The KBOS registry headings are wrong.** The coordinate-derived true
  bearing of 04L/22R is 020; Boston's variation is about 13W, so the magnetic
  course is 033 against a published ILS course of 035, and the registry's
  headingDeg of 44 is roughly nine degrees off. The 20-degree inference gate
  had been absorbing the error silently. KJFK cross-checks exactly (031 true
  + 13W = 044), so this is a KBOS data error, not a systematic one.
- **Runway names are magnetic, ADS-B tracks are true, and the legacy
  heuristic compared them anyway.** Name-times-ten is a magnetic course;
  variation at the New York fields reaches 13 degrees. The centreline path
  now gates against true courses derived from the coordinates, with the gate
  widened to 30 degrees because the live feed supplies whichever of magnetic
  heading and true track it has.

Coordinate caveat, stated where it will be found: coordinate-derived lengths
disagree with published lengths at KJFK 04L/22R, KORD 09R/27L, KATL 09L/27R
and both OMDB strips, in the pattern of pre-extension or displaced-threshold
coordinates. A threshold displaced along its own track barely moves the
extended centreline, so the data is fit for cross-track attribution and NOT
fit for touchdown-point or runway-occupancy work.
